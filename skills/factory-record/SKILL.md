# Factory の作業記録

統括セッションから、対象リポジトリで `scripts/record.py` に報告を JSON オブジェクトとして渡す。必須項目は `task` と `outcome`。完了・保留・中断のいずれでも、分かる情報を記録する。

- `agent` と `herdr_session` に元の実装担当を、`candidate_commit` に確認した候補を、`pr` に関連する PR の URL を残す。
- `checks` と `evidence` に確認結果と証跡の参照を残す。検証用 worktree を片付ける場合は、必要な証跡を後から参照できる場所に保存する。
- `observations` に停止や手戻りの原因、再発した指摘、起動手順の不足などを、発生した工程と根拠とともに残す。推測は推測と分かるように書く。

ログ全文や認証情報を含めず、必要な参照と要約を保存する。改善ループの範囲は観測の蓄積まで。作業を引き継ぐときは記録と Herdr の実行状態を照合する。

## 記録と引き継ぎの例

次は QA が一部保留になった場合の入力例。実際に観測した値と参照先に置き換える。

```json
{
  "task": "#101",
  "outcome": "ローカルでの保存を確認。外部同期の確認は保留",
  "checks": ["設定を保存して再読み込みするとオフを保持した"],
  "observations": ["QA で外部同期用のテスト接続先が未設定だった。接続先の準備後に再開できる"]
}
```

配達 ID がある報告は `event_id` に入れ、再送時には同じ JSON を渡す。スクリプトは同じタスク・同じ ID の同一内容を一度だけ保存する。内容が変わった同一 ID はエラーになるので、元の報告と照合する。別の観測には配達元が発行した別 ID を使う。ID のない従来の報告は都度追記する。応答が失われた場合は記録を照合してから再送する。

成功時にスクリプトが返した保存先を確認する。再開時は同じタスクの候補 SHA と未確認条件を拾い、現在のブランチ・PR・Herdr セッションと突き合わせる。作業途中で候補が変わっていれば、前の結果が適用できる範囲を示す。

改善材料には、どの工程で何が繰り返されたかと、その根拠を残す。「CI が不安定」だけでは原因を追えない。「同じ候補で初回は依存取得中にタイムアウト、再実行では取得成功。両実行 URL を記録」のように観測できた差を書く。

手元で作った報告を保存するときは、対象リポジトリの worktree で実行する。下の例の `report.json` は今回の結果を記入したファイルで、`FACTORY_SKILL` は読み込んだこの Skill のディレクトリを指す。

```sh
python3 "$FACTORY_SKILL/scripts/record.py" < report.json
```

比較に使う数値は、単位・対象期間・出典と一緒に保存する。同じ候補を再試行した記録は候補 SHA と実行 ID で区別する。たとえば初回失敗と再試行成功は2実行・1候補。ログが取得できず再試行回数が不明な場合は「不明」とし、観測できたゼロ回と区別する。

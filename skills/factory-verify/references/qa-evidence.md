# QA と動作証跡

- 受入条件ごとに、準備、操作、期待する結果を決める。関連する既存テストに加え、変更が利用者に届く入口で確認する。UI は操作後の表示、CLI は出力と終了コード、API は応答と必要なデータへの反映を確認する。
- プロジェクトのテスト環境と既存の操作ツールを使う。実サービスをモックに置き換えた場合は、その前提を結果に記す。
- 修正による差を主張する場合は、ベースと候補で同じ入力・操作・解決済み依存バージョン（依存更新自身が対象ならその差）を記録する。ベースでも通る場合、候補の成功は確認できるが修正による改善は判定できない。依存の準備だけで失敗したベースは比較不能として扱う。
- 指摘ごとに候補 SHA、操作手順、期待と実際の結果、関連する証跡を残す。画像、ログ、動画には認証情報や実ユーザーのデータが映り込まないようにする。証跡を固定の場所に保管する必要があれば、片付け前に統括へパスを渡す。

## 入口に合わせて観測点を選ぶ

| 対象 | 操作と観測 | 証跡に含めるもの |
| --- | --- | --- |
| UI | 対象ページが操作可能になったことを確認し、利用者と同じ操作をする。保存が条件なら新しい表示で読み戻す | 操作順、観測した表示。遷移の説明に必要なら前後の画像やトレース |
| CLI | 実際のエントリポイントに入力を渡す。出力、終了コード、生成物のうち受入条件に関係するものを調べる | 作業ディレクトリ、引数、入力例、該当する出力 |
| API | テストデータでリクエストし、契約上の応答と関連する状態変化を観測する | メソッド、パス、ステータス、必要なフィールド。永続化が条件なら読み戻し結果 |

**記載例（架空の結果）**

条件「保存後も通知がオフ」。使い捨てテストユーザーで設定を変更し、保存後に画面を再読み込み。期待はオフ、実測はオン。保存直後の表示だけはオフだった。画面の前後と読み戻し応答を候補 SHA とともに記録し、原因は未特定として統括へ渡す。

再試行でだけ通った場合は、最初の失敗と再試行の条件を残す。別の worktree でも試す場合は、同じデータベースやサーバーを共有していないかを確認し、どの候補を実際に操作したか明示する。

動的な画面では、表示されたボタンや入力欄を操作前に特定し、遷移やモーダルの開閉後に取り直す。古い要素を参照した失敗と、利用者が操作しても機能しない失敗を区別する。証跡を渡す前に実際に開き、指定の画面・値が写っているか、動画なら該当時刻を確認する。

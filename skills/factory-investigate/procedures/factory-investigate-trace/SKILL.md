# 入口から影響範囲と既存テストを追う

1. `git rev-parse HEAD` で対象を固定する。Issue に出てくる画面の文言、コマンド、設定キー、API パスなど、利用者が知っている名前を一つ選び、`rg -n` で入口を探す。同名の実装が複数あれば、ルーティングやパッケージの起動設定から実際の入口を確認する。
2. 入力 → 変換・判定 → 副作用 → 呼び出し元への戻り値を追う。保存の不具合なら読み戻し側も見る。どこから仮説かを区別し、各境界に対象コミットのファイル・行またはシンボルを添える。
3. 関係する既存テストの入力とアサーションを読む。「テストがある」と「今回の条件を観測している」を区別する。CI、Makefile、パッケージ設定から、そのテストを実行する場所とコマンドを確認する。
4. 複数の原因が残ったら、それぞれを区別できる最小の観測を返す。実行していないコマンドは「確認候補」と記す。

### 引き継ぎ例

この Factory の Hook で「実装依頼を説明依頼と区別したい」場合、入口は `hooks/user_prompt_submit.py` の `route`、文面の判定は `matches`。前者では Plan モードや子 worktree でも分岐する。関連テストは `tests/test_factory.py` の `PromptRouting`。正規表現だけを変える案では、起動場所による抑止を説明できない。実際の報告には調べた SHA と行を付け、ユーザーの入力でどの分岐に入ったか未確認なら、その旨を残す。

同じ症状が入力・保存・読み戻しのどこでも起こり得るときは、境界ごとにデータ表現を並べる。たとえば「未指定」と「明示的な偽値」が同じ既定値に変換される箇所を探し、保存値を読むだけで切り分けられるかを実装担当に渡す。

## 判断例

同名の save が UI と CLI にある場合、起動設定から報告された入口へつながる方を選ぶ。両方が共通ストアに到達するなら、表示だけの不具合か保存値の不具合かを識別できる観測を一つ添える。

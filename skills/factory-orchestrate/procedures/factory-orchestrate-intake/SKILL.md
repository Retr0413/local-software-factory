# Issue の受入条件と割り当てを決める

依頼と既存の会話から対象リポジトリと Issue を特定する。Issue 番号だけの場合は、対象リポジトリを確認する。対象が特定できなければ質問する。Issue 調査だけの依頼は調査として扱う。

受入条件は利用者が観測できる文にする。「保存を直す」なら、保存操作、再読み込み、期待する表示を特定する。依頼文だけでは期待値が決まらないときは、既存仕様とテストを調査役に確認させる。両者が食い違い、選択によって利用者の挙動が変わるときに、その違いを人に返す。

| 起動前に見つかった関係 | 割り当て |
| --- | --- |
| 別々の機能で、単独で受入条件を満たせる | 同じバッチに入れ、それぞれの担当に独立した完了条件を渡す |
| B のテストが A の新しい公開 API を使う | A の結果を確認後、そのコミットを含むベースから B を起動する |
| 同じファイルに触れるが依存の有無が不明 | 変更する契約と範囲を照合する。競合が避けられなければ順に割り当てる |

性能改善なら、入力規模、比較対象、観測する指標を合わせる。たとえば「一覧を高速化」では、同じ件数・同じキャッシュ条件で比較する。数値目標が依頼にない場合はベースと候補の実測値を返し、独自の合格ラインを設けない。調査だけの依頼なら、終了条件は「次の判断に必要な問いへ根拠付きで答えられたか」とする。

担当への依頼例（架空の Issue）

「#101、通知設定の保存。設定をオフにして再読み込みするとオフのまま。未設定の利用者は従来の初期値。対象は設定画面と保存処理。保存後の表示と読み戻しを確認する。候補 SHA と実行結果を返す。今回の依頼はローカル実装まで。」

保留は Issue ごとに管理する。依存待ちは先行変更を含むコミット、容量待ちは利用可能な枠、受領不明は元の会話での受領確認を再開条件にする。一部が保留でも、独立して進められる仕事はその受入条件に沿って進める。

受け取ったコミットを後続の base に渡す際は、起動元リポジトリで `git cat-file -e "<SHA>^{commit}"` が成功するかを確認する。別のローカル複製だけにある場合は、その複製でのテスト結果と、起動元への引き継ぎ待ちを区別する。

## 判断例

A が新形式を保存し B がその形式を読む場合、B の実装には A を含むベースが要る。画面文言だけを直す独立の C は先に渡せる。割当表には Issue ごとのベース、観測する結果、開始条件を残す。

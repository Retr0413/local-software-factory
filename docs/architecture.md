# Factory 全体設計

## 目的

ローカルのリポジトリに対して、調査、機能追加、バグ修正、QA、レビューを進められる Software Factory を作る。作業中の状態と結果を追跡でき、Codex または Claude Code を利用できる構成とする。

## 基本方針

- 人間の依頼または GitHub Issue を起点にする。
- 統括が目的、受入条件、依存関係、作業範囲を整理する。
- 1 Issue または独立した1タスクにつき、実装セッションを1つ割り当てる。同一タスクの実装と指摘修正はその担当が継続する。
- 調査、QA、独立レビューは必要に応じて実装担当を支援する。
- 依存のないタスクは別 worktree で並行し、依存するタスクは必要な成果を取り込める順に開始する。
- 検証結果と証跡を人が確認できるようにし、改善に役立つ情報を蓄積する。
- 実行エンジンとして Codex と Claude Code の選択肢を設ける。各 CLI の認証、権限、契約、利用可能な機能はそれぞれに従う。

## 全体像

```text
人間 / GitHub Issue
         |
         v
統括セッション
  - 目的と受入条件の整理
  - タスク・依存関係・担当の管理
         |
         +-----------------------+
         |                       |
         v                       v
  タスク A の worktree     タスク B の worktree
  実装担当 Codex/Claude    実装担当 Codex/Claude
         |                       |
  調査 / QA / レビュー     調査 / QA / レビュー
         |                       |
         +-----------+-----------+
                     v
               検証・証跡
                     |
              統括と人間が確認
                     |
                     v
            実行記録・改善情報の蓄積
```

実装担当は各タスクで一人とする。複数のタスクが同じ場所を変更する場合は、その依存と衝突を統括が判断する。検証結果は対象コミットと結びつけ、変更後は必要な確認をやり直す。

## コンポーネント

| 要素 | 役割 |
| --- | --- |
| 統括 | 依頼の整理、タスク割当、依存関係、実行状態、結果と証跡を管理 |
| 実装担当 | 担当タスクのコード変更、適切なテスト、レビュー指摘への対応 |
| 調査 | 関連コード、仕様、ログ、既存 Issue などの情報を収集 |
| QA | 受入条件と実動作を確認し、結果と証跡を作成 |
| 独立レビュー | 変更と既存動作への影響を確認し、根拠ある指摘を返す |
| Herdr | セッション、エージェント、ペイン、worktree の起動・観測を支援 |
| 実行環境 | リポジトリ、依存、テストデータ、起動手順、必要なモックを提供 |
| 記録 | タスク、実行状態、対象コミット、確認結果と改善情報を紐づける |

GitHub は Issue と PR の連携先の一つとする。人間のローカルな依頼も扱う。実装担当の割り当てと作業記録は、リポジトリの共通 Git ディレクトリに保持する。

## 実行環境

プロジェクトが定義する起動・停止・テスト手順を再利用する。外部連携のモック、サンプルデータ、ブラウザ操作などを必要に応じて用意し、QA がユーザー視点で確認できるようにする。worktree は Git の作業分離であり、実行プロセスのセキュリティ隔離を意味しない。使用する CLI や実行環境に応じた権限設定が必要である。

## 開発の進め方

1. 手動の統括で、1タスクの実装・検証・記録を完走する。
2. 独立した複数タスクを Herdr で並行し、状態や依存を追えるようにする。
3. Codex と Claude Code の起動・再開・状態確認を、それぞれの CLI に合わせて検証する。
4. 受入条件、テスト、レビュー、証跡を運用に組み込む。
5. 記録した改善情報の活用方法と自動化範囲を別途設計する。
